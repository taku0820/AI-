## 1. バックアップの安全な実行方法

```bash
python hive_backup.py create
```

- 対象DBはプロジェクト内の `ai_company.db` に固定されている（コード上
  固定であり、CLI引数・環境変数での変更はできない）
- 元DBは読み取り専用（SQLiteの `mode=ro` URI接続）で開かれ、バックアップ
  作成中に一切変更されない
- コピーには SQLite公式の Online Backup API
  （`sqlite3.Connection.backup()`）を使用する。単純な `cp` によるファイル
  コピーと異なり、DBが書き込み中であっても壊れたスナップショットになら
  ない、SQLiteが推奨する安全な方式
- 実行するたびに `backups/backup_<日時>_<ランダム6文字>/` という専用
  ディレクトリが新規作成される。既存バックアップの上書き・自動削除は
  一切行わない（ディスク容量が気になる場合は、後述4章の方針に従い
  手動で判断する）
- 対象は `work_logs`・AI Hive OSの7テーブル・`audit_logs` を含む
  `ai_company.db` **ファイル全体**であり、特定テーブルだけを選んで
  バックアップする機能はない（DB全体を単一のファイルとしてコピーする
  ため）

実行結果の例:

```
バックアップを作成しました: backups/backup_20260904_213645_374d29
  作成日時: 2026-09-04T21:36:45
  SHA-256: 9c5002130e3b...
  整合性チェック: ok
  外部キー整合性: 問題なし
    audit_logs: 3件
    ...
    work_logs: 3件
```

作成された各バックアップディレクトリには以下が含まれる。

| ファイル | 内容 |
|---|---|
| `ai_company.db` | バックアップ時点のDB全体のコピー |
| `metadata.json` | 作成日時・SHA-256ハッシュ・整合性チェック結果・外部キー整合性・テーブル別件数 |

## 2. バックアップをGit・クラウド共有・スクリーンショットへ含めない注意

- `backups/` ディレクトリおよび `ai_company.db` は、プロジェクトの
  `.gitignore` に既に登録されており、`git status` にも表示されない
  （本MISSIONでもこの設定は変更していない）
- `git add -A` 等の一括ステージや、`.gitignore` を無視する `git add -f`
  を **backups/・ai_company.db に対して使わないこと**。誤って追跡対象に
  してしまうと、業務データ・監査ログが丸ごとGit履歴に残ってしまう
- バックアップディレクトリ（`ai_company.db`・`metadata.json`）を、Slack・
  クラウドストレージ（Google Drive等）・チャットへの添付など、Git以外の
  経路で外部共有しないこと。DB全体には `employees` 等の内部業務データ・
  `audit_logs`（操作履歴）が含まれる
- ターミナルで `hive_backup.py create` の出力（テーブル別件数等）を
  スクリーンショットする場合も、業務データの件数自体が意図せず外部へ
  出ないよう配布先に注意すること
- コミット前は、これまでのMISSION同様 `git status` / `git diff --cached`
  で `backups/`・`ai_company.db` がステージされていないことを確認する
  運用を徹底する

## 3. バックアップ検証方法

```bash
python hive_backup.py verify backups/backup_20260904_213645_374d29
# または、DBファイルを直接指定してもよい
python hive_backup.py verify backups/backup_20260904_213645_374d29/ai_company.db
```

- 検証は完全に読み取り専用で行われる。対象のバックアップDB・元の
  `ai_company.db` のいずれも変更しない
- 確認内容は以下の3点:
  1. バックアップDBファイルのSHA-256ハッシュが、作成時に記録した
     `metadata.json` の値と一致するか（改変検知）
  2. `PRAGMA integrity_check` が `ok` を返すか
  3. `PRAGMA foreign_key_check` が違反なしを返すか
- 上記すべてを満たした場合のみ「総合判定: OK」となる。1つでも欠けると
  「総合判定: NG」となり、CLIは終了コード1を返す
- `backups/` 配下から外れたパス（プロジェクト外のパス、パス
  トラバーサル等）を指定した場合や、指定したバックアップが存在しない
  場合は、検証を実行せず安全にエラーで終了する

実行結果の例:

```
検証対象: /Users/.../backups/backup_20260904_213645_374d29/ai_company.db
  記録済みハッシュ一致: はい
  整合性チェック: ok
  外部キー整合性: 問題なし
  総合判定: OK
```

## 4. 保持方針（自動削除・自動上書きは行わない）

- `hive_backup.py` は、古いバックアップの自動削除・世代管理・自動上書きを
  一切行わない。バックアップは作成するたびに増え続ける
- ディスク容量やバックアップ数が気になった場合も、**手動で内容を確認し、
  必要性を判断した上で人手で削除する**運用とする（自動化された削除は
  意図しないバックアップ消失のリスクがあるため、本MISSIONではあえて
  実装していない）

## 5. 障害発生時にまず行うこと（復元の判断材料集め）

実際に復元は行わず、以下の情報を集めて状況を整理する。

1. `python hive_backup.py verify <対象バックアップ>` を実行し、
   利用可能な最新バックアップが「総合判定: OK」であるかを確認する
2. `ai_company.db` の現在の状態を確認する（例: サーバー起動時の
   エラーメッセージ、`sqlite3 ai_company.db "PRAGMA integrity_check"`
   の結果など）。この確認自体でDBを変更しないよう、書き込みを伴う
   操作は行わない
3. どの時点のバックアップまで遡る必要があるかを、各バックアップの
   `metadata.json` の `created_at`・テーブル別件数から見積もる
4. 影響範囲（`work_logs`・AI Hiveの7テーブル・`audit_logs` のうち、
   何が壊れている/失われているか）を整理する

## 6. 復元前の確認項目（実復元は個別承認が必要）

**本MISSIONでは実DBへの復元機能を一切実装・実行していない。** 将来、
実際に復元を行う場合は、着手前に必ず以下を確認し、利用者の個別承認を
得ること。

- [ ] 復元対象ファイル: どのバックアップ（`backups/backup_<日時>_<suffix>/`
      のどれ）を使うか、`verify` で「総合判定: OK」であることを確認済みか
- [ ] バックアップ日時: `metadata.json` の `created_at` が、復元したい
      時点として妥当か（それより新しい正常なデータを失うことにならないか）
- [ ] 復元先: 本番の `ai_company.db` をそのまま置き換えるのか、別名で
      並行稼働させて内容を見比べるのかを明確にする
- [ ] サーバー停止手順: `app.py` のプロセスを止めてから復元するのか
      （稼働中のDBファイルを直接置き換えるのは事故のもとであり、原則
      サーバー停止後に行うべきである）
- [ ] 復元後の再起動・動作確認手順（`GET /`・`GET /api/logs`・Hive APIの
      簡易確認、既存55テスト＋本MISSIONの14テストの再実行）
- [ ] 復元によって失われるデータ（バックアップ以降に追加された
      `work_logs`・Hiveデータ・`audit_logs`）がないか、あるとすれば
      それを許容できるか

上記が揃い、利用者の明示的な承認を得てから、復元作業を後続MISSIONとして
計画する。

## 7. 外部公開・外部AI接続とは無関係であること

- `hive_backup.py` はファイルシステム上のローカル操作のみを行い、
  ネットワーク通信・HTTPサーバーへの接続を一切行わない（`hive_admin.py`
  のようなHTTPクライアントではない）
- 本ツールの追加は、`docs/MISSION009_auth_design.md` 3.6節・
  `docs/MISSION014_local_audit_view_design.md` 7章・
  `docs/MISSION015_admin_cli_runbook.md` 7章で維持してきた
  「localhost限定運用・外部公開なし・外部AI接続なし」の方針に一切影響
  しない
- バックアップ・検証機能の外部公開（クラウドへの自動アップロード等）や、
  外部AI（GPT・Gemini等）からのバックアップ操作は、本MISSIONでは一切
  想定・許可しない。将来検討する場合も別途利用者の承認が必要
