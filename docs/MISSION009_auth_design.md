## 2. 脅威モデル

### 2.1 localhost限定運用で想定するリスク（現状の運用形態）

| リスク | 内容 | 現状の緩和策 |
|---|---|---|
| 同一Mac内の他プロセスからの誤アクセス | 同じMac mini上で動く他のスクリプト・ツールが誤って書き込みAPIを叩く | 現状は緩和策なし（認証なし＝同一マシン上の任意プロセスから書き込み可能） |
| 開発中の誤操作 | curlやテストスクリプトの誤ったコマンドで本番Hiveデータを書き換える | MISSION 007で手順化した「PoCデータの識別・安全削除」フローのみ |
| デバッグモード（`debug=True`）由来のリスク | Werkzeugデバッガが有効な場合、エラー画面から任意コード実行が可能になるケースがある（Werkzeugの既知の設計） | localhost限定のためリスクは限定的だが、デバッガPINが漏洩・推測された場合に影響が生じ得る |

### 2.2 誤ってLANやインターネットへ公開された場合のリスク（想定シナリオ、現状は未発生）

| リスク | 内容 |
|---|---|
| 無認証での全データ読み取り | `employees`/`missions`/`tasks`等の内部業務データが第三者に閲覧される |
| 無認証での書き込み・改ざん | 第三者が任意のMISSION/TASK/PROPOSAL/DECISIONを登録・改変できる。特に`decisions`テーブルは「誰が承認したか」の記録であり、なりすまし登録のリスクが大きい |
| Werkzeug開発サーバーの利用 | 本番運用に耐えない開発用サーバーのまま公開されると、可用性・セキュリティ双方でリスクが大きい（`debug=True`はコード実行リスクも伴う） |
| DoS的な過負荷 | レート制限が存在しないため、単純な連続リクエストでSQLite書き込みが輻輳する可能性 |

**現状の担保**: MISSION 008で `host="127.0.0.1"` に固定し、`0.0.0.0`バインドを行わない設計としたため、上記シナリオは「意図的にコードを変更しない限り発生しない」状態にある。本設計文書はこの前提を今後も維持することを推奨する。

### 2.3 APIトークンの漏えい、ログ出力、Git混入のリスク（将来、認証導入後を想定）

| リスク | 内容 | 対策方針（3章で詳述） |
|---|---|---|
| トークンのGitコミット混入 | `.env`ファイルや設定ファイルに直書きしたトークンを誤ってコミットする | `.gitignore`に`.env`を登録、コードレビューでの目視確認、可能であればpre-commitでの秘密情報スキャン |
| ログへのトークン出力 | アクセスログやエラーログにAuthorizationヘッダーの値がそのまま出力される | ログ出力時にAuthorizationヘッダーの値をマスクする実装ルールを設ける |
| レスポンスへのトークン混入 | エラーレスポンスのメッセージにリクエストヘッダーの中身をそのまま含めてしまう | エラーメッセージは固定文言とし、リクエスト内容をエコーしない |
| 環境変数の露出 | プロセスの環境変数がクラッシュダンプや`ps`コマンド等で露出する | Mac mini上のローカル利用に限定し、多要素の防御は求めないが、環境変数名・値をコード中にハードコードしない運用を徹底する |

### 2.4 書き込みAPIの不正利用・誤操作のリスク

| リスク | 内容 |
|---|---|
| 権限のない主体によるMISSION発行・DECISION登録 | 現状は「誰でも」書き込み可能なため、`issued_by`/`decided_by`等のフィールドは自己申告であり検証されない（なりすまし可能） |
| 大量データ投入によるDB肥大化 | レート制限・件数制限がないため、誤ったループ処理等で大量データが投入される可能性 |
| 外部キー制約違反時の情報開示 | 現状`FOREIGN KEY constraint failed`のような内部エラー文言がそのままクライアントに返る（MISSION006 PoCで確認済み）。認証・権限機構がない現状では大きな問題ではないが、将来外部公開する場合は内部実装の詳細を返さない方針にすべき |

## 3. 後続MISSIONで実装する認証仕様案

**本章は仕様案であり、今回のMISSION 009では一切実装しない。**

### 3.1 認証方式

- 新規Hive API（1.2節の17エンドポイント）に対し、`Authorization: Bearer <token>` ヘッダーによる認証を候補とする
- 既存エンドポイント（`/`, `/api/logs`）は当面認証対象外とする（互換性維持のため。4.1節参照）
- トークンは単純な共有シークレット（固定文字列の完全一致比較）を最小実装の候補とし、将来的にトークンごとの権限・失効管理が必要になった場合はテーブル管理方式へ拡張する（その場合は別途DBスキーマ変更が必要になるため、本MISSIONの範囲外・要承認事項とする）

### 3.2 秘密情報の管理方針

- トークンはソースコード・SQLite（`ai_company.db`）・Git履歴・ログのいずれにも保存しない
- 環境変数（例：`AI_HIVE_API_TOKEN`）でのみ管理する
- `.env`ファイルを利用する場合は必ず`.gitignore`に登録し、リポジトリに含めない
- サンプル・テンプレートとして`.env.example`（値を含まないキー名のみのファイル）を用意することは許容されるが、これも今回のMISSIONでは作成しない（「APIキー、トークン、`.env`、認証コードを作成しない」という制約に基づく）

### 3.3 認証失敗時のレスポンス方針

- 情報を出しすぎない統一エラー形式を用いる：
  ```json
  {"status": "error", "message": "認証に失敗しました。"}
  ```
- トークンが「存在しない」「不正」「期限切れ」等の詳細理由をレスポンスに含めない（総当たり攻撃・情報収集を助けないため）
- HTTPステータスは401（未認証）または403（権限不足）を使い分ける

### 3.4 権限分離案（読み取り／書き込み／管理操作）

| 権限レベル | 対象操作 | 想定トークン種別 |
|---|---|---|
| 読み取り（read） | GET系17エンドポイント中の全読み取り | 読み取り専用トークン |
| 書き込み（write） | POST/PATCH（`/api/proposals/<id>`を除く通常の登録・更新） | 読み書きトークン |
| 管理操作（admin） | `PATCH /api/proposals/<id>`（意思決定の承認・却下に相当）、将来追加され得るDELETE系API | 管理者トークン |

外部AI（GPT/Gemini等）に付与するトークンは、原則として**read権限のみ、または特定のwrite操作に限定したスコープ付きトークン**を推奨する。admin権限を外部AIに直接渡すことは推奨しない。

### 3.5 認証・認可・監査ログ・レート制限の分離設計方針

- **認証（Authentication）**: トークンの有効性検証のみを担う独立した関数/ミドルウェアとする
- **認可（Authorization）**: トークンが持つ権限レベル（3.4節）とリクエスト対象操作の照合を、認証とは別の層で行う
- **監査ログ（Audit Log）**: 誰が（どのトークン/主体が）・いつ・何を実行したかを記録する仕組みを別途設ける。これは`work_logs`とは別の新規テーブルとして設計することを想定するが、**DBスキーマ変更を伴うため、本MISSIONでは設計方針の提示のみとし、実装・スキーマ確定は別MISSIONでの承認を要する**
- **レート制限（Rate Limiting）**: 認証・認可と独立したミドルウェアとして設計し、書き込みAPIを優先的に対象とする

### 3.6 将来のlocalhost以外への公開について

- localhost以外（LAN・インターネット）への公開を検討する場合は、以下を**必須条件**とする
  1. 3.1〜3.5の認証・認可機構の実装完了
  2. HTTPS化（現状のWerkzeug開発サーバーではなく、本番向けWSGIサーバー＋TLS終端の導入）
  3. 利用者からの明示的な承認（本MISSIONの停止条件と同様、実装前に必ず承認を得る）
- 上記が満たされない限り、`host="127.0.0.1"`固定を維持する

## 4. 実装前提条件とテスト計画

### 4.1 実装に必要な承認事項（後続MISSIONで実装着手前に確認すべき事項）

1. 認証対象を「新規Hive APIのみ」とし、`/`・`/api/logs`は対象外のままとする、という前提でよいか
2. トークン方式は最小実装（環境変数1本の共有シークレット）から始めてよいか、それとも初回からトークンごとの権限管理（DB管理）が必要か
   - 後者を選ぶ場合はDBスキーマ変更が発生するため、別途承認が必要
3. 監査ログ用の新規テーブルを追加してよいか（DBスキーマ変更を伴うため要承認）
4. レート制限の要否・閾値
5. `.env`運用を許可するか（`.gitignore`登録前提で、リポジトリに`.env.example`を追加してよいか）

### 4.2 互換性を壊さないテスト項目（実装時に必須）

- `GET /`、`GET /api/logs` が認証なしで従来通り200を返すこと（回帰）
- `work_logs`のデータ・スキーマが変更されていないこと
- 既存の`test_hive_api.py` 8件が全てPASSし続けること
- 新規Hive APIの既存レスポンス形式（`{"status": "success"/"error", ...}`）が認証追加後も変わらないこと

### 4.3 トークンがログ・レスポンス・Git差分へ露出しないことの確認方法

- アプリのログ出力（Flaskの標準アクセスログ、独自ログを追加する場合はそのログ）にAuthorizationヘッダーの生値が出力されないことを、実際にリクエストを送って標準出力・ログファイルを目視確認する
- エラーレスポンスのJSONにリクエストヘッダー・トークン文字列が含まれないことを、認証失敗時のレスポンスボディを確認する
- `git diff`・`git status`で`.env`やトークンを含むファイルがステージされていないことを、コミット前に必ず確認する（本プロジェクトのMISSION 005以降で徹底してきた「commit前にgit diff --cachedで対象確認」の運用をそのまま踏襲する）

### 4.4 認証テストの方針（4パターン）

| ケース | 期待結果 |
|---|---|
| 認証なしアクセス（Authorizationヘッダーなし） | 401、統一エラー形式 |
| 無効トークン | 401、統一エラー形式（理由の詳細は返さない） |
| 有効トークン・権限あり | 200/201、通常のレスポンス |
| 有効トークン・権限不足（read権限でwrite操作等） | 403、統一エラー形式 |
