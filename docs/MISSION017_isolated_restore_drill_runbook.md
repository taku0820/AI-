# localhost限定 隔離復旧訓練 手順書（MISSION 017）

対象ファイル: `hive_backup.py`（`restore-test` サブコマンドを本MISSIONで追加。
`create`・`verify` はMISSION 016で追加済み）

作成時点のブランチ: `claude/company-dashboard-sqlite-mjoexa`
作成時点のHEAD: `98192a69a179020bffd789bcd4099486a69bfc83`（MISSION 016完了時点）

---

## 1. 隔離復旧訓練の目的

- バックアップ（`docs/MISSION016_backup_recovery_runbook.md` で整備した
  `hive_backup.py create`/`verify`）が「実際に復旧可能な状態か」を、
  **本番の `ai_company.db` に一切触れずに**確認するための訓練
- 障害が実際に起きたときに慌てて本番DBへ直接手を出すのではなく、事前に
  「このバックアップは中身も正しく復元できる」ことを確認しておくための
  日常的な健全性チェックとして使う
- `restore-test` はバックアップDBを一時領域へ複製し、整合性・外部キー
  整合性・テーブル件数を検証するだけであり、**本番環境の復旧そのもの
  ではない**（実復旧は6章参照）

---

## 2. 実DBを復元先にしてはいけないこと

- `hive_backup.py restore-test` は、復旧先を **`tempfile`が新規作成する
  完全な一時ディレクトリ**にコード上で固定している
- 復旧先をCLI引数・環境変数で指定できるオプションは存在しない（誤って
  `ai_company.db` や `backups/` 配下を復旧先に指定してしまう余地が
  そもそも無い）
- コード内には、生成された一時ディレクトリが誤ってプロジェクトルート
  （＝`backups/`・`ai_company.db`を含む）の配下に入っていないかを都度
  確認する追加チェックも入っており、該当した場合は復旧コピーを行わず
  中止する
- **`restore-test` は `ai_company.db` に対して一切の書き込みを行わない。**
  読み書きするのは「バックアップDB(読み取り専用)」と「一時領域内の
  復旧先DB(訓練終了後に削除)」だけである

---

## 3. バックアップ検証後に訓練を行う順序

`restore-test` は、内部で必ず最初に `verify`（MISSION 016で追加した
検証処理）を実行し、**検証済みのバックアップだけ**を復旧コピーの対象に
する。改変済み・破損・パスが不正なバックアップは、復旧コピーを試みる
前に安全に拒否される。

```bash
# 1. まずバックアップを作成する(未実施の場合)
python hive_backup.py create

# 2. 作成したバックアップを検証する(総合判定: OK であることを確認)
python hive_backup.py verify backups/backup_20260904_213645_374d29

# 3. 検証済みのバックアップに対して隔離復旧訓練を実行する
python hive_backup.py restore-test backups/backup_20260904_213645_374d29
```

`verify`をスキップしていきなり`restore-test`を実行しても、内部で自動的に
`verify`相当のチェックが行われるため安全性は保たれる。ただし、事前に
`verify`を単独実行して結果を確認しておくと、「検証で落ちたのか」
「訓練固有の問題（件数不一致等）で落ちたのか」を切り分けやすい。

---

## 4. 一時領域だけを使う仕組み

- 復旧先は `tempfile.mkdtemp(prefix="hive_restore_drill_")` が生成する
  ディレクトリ（macOSでは通常 `/private/var/folders/.../T/` 配下）
- コピーには `create`/`verify` と同じ SQLite公式 Online Backup API
  （`sqlite3.Connection.backup()`）を使用し、バックアップDB側は読み取り
  専用接続で開く
- 復旧後、一時DBに対してのみ以下を確認する:
  1. `PRAGMA integrity_check` が `ok` を返すか
  2. `PRAGMA foreign_key_check` が違反なしを返すか
  3. テーブル別件数が、バックアップの `metadata.json` に記録された件数と
     一致するか
  4. 訓練の前後で、バックアップ元DBファイルのSHA-256ハッシュが変化して
     いないか
- 上記の確認が終わり次第、**成功・失敗を問わず**一時ディレクトリを
  `shutil.rmtree()` で削除する（`try/finally`で保証している）。訓練後、
  プロジェクト内にも一時領域にも復旧先DBは一切残らない

## 5. 訓練成功・失敗時の確認項目

### 5.1 成功時（総合判定: OK）

```
隔離復旧訓練: backups/backup_20260904_213645_374d29 を一時領域へ復旧しました。
  一時領域(訓練後に削除済み): /private/var/folders/.../hive_restore_drill_xxxxxx
  整合性チェック: ok
  外部キー整合性: 問題なし
  テーブル件数の一致(metadata.json比較): 一致
  バックアップ元ハッシュ不変: はい
  総合判定: OK
```

- このバックアップは「複製しても中身が壊れておらず、記録された件数
  通りに復元できる」ことが確認できた状態
- 定期的にこの訓練をPASSさせておくことが、障害時に安心して復旧判断を
  下すための材料になる

### 5.2 失敗時（総合判定: NG、終了コード1）

| 症状 | 主な原因 | 対応 |
|---|---|---|
| `verify`の時点でBackupErrorとなり訓練が始まらない | バックアップが改変・破損している、`backups/`外のパスを指定した、指定パスが存在しない | 該当のバックアップは復旧に使わない。より新しい別のバックアップで`verify`からやり直す |
| 整合性チェックが`ok`以外 | 一時領域への複製後にDBが壊れている(まれ。コピー元自体が既に壊れている可能性が高い) | そのバックアップを復旧に使わない。1世代前のバックアップで再訓練する |
| 外部キー整合性に違反あり | バックアップ時点のDB自体に外部キー不整合があった可能性 | `docs/MISSION009_auth_design.md`等を参照し、原因調査を優先。復旧の可否は個別判断 |
| テーブル件数が不一致 | `metadata.json`が期待する件数と、実際に複製されたDBの件数が異なる(理論上は複製処理自体の異常时のみ発生するはず) | 同じバックアップで`restore-test`を再実行して再現するか確認。再現する場合はそのバックアップを使わない |
| バックアップ元ハッシュが変化 | `restore-test`実行中にバックアップファイルが外部から書き換えられた(別プロセスによる上書き等) | バックアップファイルの取り扱いを見直す。該当バックアップは信頼せず、新たに`create`し直す |

いずれの失敗も、**訓練失敗＝実DBへの影響では一切ない**（`ai_company.db`
には最初から一度も書き込みアクセスしていない）。失敗したバックアップを
今後の復旧候補から除外し、より新しい・正常なバックアップを使うことが
基本方針となる。

## 6. 実復元には別途の個別承認が必要であること

- **本MISSIONでも、実DB(`ai_company.db`)への復元（上書き・削除・置換）は
  一切実装・実行していない。** `restore-test` はあくまで「一時領域での
  検証訓練」であり、本番復旧のコマンドではない
- 実際に本番DBを復旧する場合は、`docs/MISSION016_backup_recovery_runbook.md`
  6章の確認項目（復元対象ファイル・バックアップ日時・復元先・サーバー
  停止手順・復元後の動作確認手順・失われるデータの許容可否）をすべて
  満たした上で、利用者の明示的な個別承認を得てから、別MISSIONとして
  計画・実施すること
- `restore-test`で「総合判定: OK」を確認できたことは、あくまで「その
  バックアップの中身が壊れていないこと」の裏付けであり、実復元の
  実施可否そのものを承認するものではない

---

## 7. 外部公開・外部AI接続とは無関係であること

- `restore-test`を含む `hive_backup.py` は、ファイルシステム上の
  ローカル操作のみを行い、ネットワーク通信・HTTPサーバーへの接続を
  一切行わない
- 本機能の追加は、`docs/MISSION009_auth_design.md` 3.6節・
  `docs/MISSION014_local_audit_view_design.md` 7章・
  `docs/MISSION015_admin_cli_runbook.md` 7章・
  `docs/MISSION016_backup_recovery_runbook.md` 7章で維持してきた
  「localhost限定運用・外部公開なし・外部AI接続なし」の方針に一切影響
  しない
- 復旧訓練機能の外部公開や、外部AI（GPT・Gemini等）からの実行は、本
  MISSIONでは一切想定・許可しない

## 8. まとめ（本MISSIONでの成果）

- `hive_backup.py` に `restore-test` サブコマンドを追加した。検証済み
  バックアップのみを入力とし、プロジェクト外・`backups/`外・
  `ai_company.db`とは絶対に重ならない一時領域へのみ復旧コピーし、
  訓練後は一時領域を確実に削除する
- 実DB(`ai_company.db`)への復元・上書き・削除は一切実装・実行していない
- 本手順書に、訓練の目的・実DBを対象にしない設計・実行順序・一時領域
  だけを使う仕組み・成功/失敗時の確認項目・実復元に必要な個別承認・
  外部公開との無関係性を整理した
