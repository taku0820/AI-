# localhost限定 監査ログ運用画面 設計文書（MISSION 014）

本書は設計文書であり、ダッシュボードUIの実装は含まない。ここに記載した
仕様は、後続MISSIONでの画面実装承認を得るための「仕様案」であり、確定
した実装ではない。

作成時点のブランチ: `claude/company-dashboard-sqlite-mjoexa`
作成時点のHEAD: `6eca697235089ee4760afcb16a3cde768637da26`（MISSION 013完了時点）

## 1. 運用画面の目的

- 対象利用者: admin権限を持つ利用者（柴犬社長・開発運用者）のみ
- 目的: `GET /api/audit-logs` が返す監査記録（認証失敗・権限不足・
  レート制限超過・admin操作・主要なデータ変更）を、コマンドラインで
  curlを叩かなくても目視で確認できるようにする、軽量な参照専用画面
- 想定利用シーン: 「最近401/403が多発していないか」「意図しない
  write/admin操作が記録されていないか」を運用者が数分で確認するための
  補助ツールであり、業務システムの主画面ではない
- 位置づけ: あくまで**localhost限定**の内部ツール。社外・他端末からの
  利用は想定しない（7章参照）

## 2. adminトークンの非保存方針（最重要方針）

画面実装にあたり、adminトークンは以下のいずれの場所にも**保存・埋め込み
しない**。

| 保存先候補 | 方針 |
|---|---|
| HTML（静的ファイル・テンプレート） | トークン文字列をハードコードしない。ビルド時・テンプレート展開時にも埋め込まない |
| JavaScript（フロントエンドコード） | ソース中に定数として書かない。バンドル・minify後の成果物にも残らないことを確認する |
| `localStorage` / `sessionStorage` | 保存しない。ブラウザの開発者ツールやXSSで容易に読み取られるため、監査ログ参照という管理者専用機能とは相性が悪い |
| Cookie | 保存しない（HttpOnly化しても、ローカル単一ユーザー運用でCookie管理の複雑さに見合うメリットがない。3章の代替案を参照） |
| URL（クエリパラメータ・フラグメント） | トークンをURLに含めない。ブラウザ履歴・アクセスログ・リファラへの漏えいリスクがあるため |
| サーバー側ログ・Flaskアクセスログ・`_record_audit_log`が書き込む`audit_logs` | 既存 `hive_db.require_permission` の設計方針（Authorizationヘッダー・トークン・環境変数値・リクエスト本文を記録しない）を画面経由の呼び出しでも維持する |

この方針は、既存の `docs/MISSION009_auth_design.md` 3.2節（秘密情報の
管理方針）・`hive_db.py` の `require_permission` docstring（実トークンは
環境変数からのみ読み取り、コード・ログ・レスポンスに一切出力しない）と
整合させる。

## 3. 画面実装前に必要なブラウザ認証方式の判断事項

現状の `GET /api/audit-logs` は `Authorization: Bearer <admin_token>`
ヘッダーによる認証のみをサポートしており、ブラウザから直接この形式で
毎回ヘッダーを付与する標準的な仕組み（ブラウザネイティブの機能）は
存在しない。画面を実装する前に、以下を承認・決定する必要がある。

### 3.1 候補A: リクエストの都度、利用者がトークンを手入力する

- 画面を開くたびに（または初回のみ）admin トークンをフォームに入力し、
  JavaScriptの変数（**保存はしない**・ページリロードで消える）として
  保持し、`fetch` の `Authorization` ヘッダーに都度付与する
- 長所: どこにも永続化しないため、2章の非保存方針を最も単純に満たせる
- 短所: 画面を開くたび／再読み込みのたびに毎回入力が必要で利便性が低い

### 3.2 候補B: サーバー側セッション＋別建てのログインを追加する

- 画面用に別途「ログイン」の概念を導入し、サーバー側でセッションを
  管理する（Cookieはセッション識別子のみを持ち、adminトークン自体は
  Cookieに入れない）
- 長所: 利用者体験は改善する
- 短所: 新しい認証機構・セッション管理・（必要であれば）DBスキーマ
  変更を伴う可能性があり、本MISSIONの範囲（DBスキーマ変更禁止・設計
  文書のみ）を超える。要別途承認

### 3.3 候補C: サーバー側プロセス環境変数を画面のバックエンドが直接参照する

- 画面をFlask側の別ルートとして実装し、サーバープロセス自身が環境変数
  `AI_HIVE_ADMIN_TOKEN` を読んで `/api/audit-logs` 相当の処理を内部的に
  呼び出す（ブラウザにトークンを一切渡さない）
- 長所: ブラウザ側にトークンが渡らないため2章の方針を最も強く満たせる
- 短所: 「誰がその画面を開いているか」を区別できない（localhost上の
  任意プロセス・任意ブラウザタブが無条件でadmin相当の参照ができて
  しまう）。localhost限定運用でのリスク許容度の判断が必要

### 3.4 本書時点の推奨

- 初期実装は **候補A（都度手入力・非永続）** を推奨する。理由:
  - 2章の非保存方針を実装ミスの余地なく満たせる
  - 新しい認証機構やスキーマ変更を伴わず、本MISSIONの制約
    （DBスキーマ変更禁止・commit/push禁止）の範囲内で完結する設計として
    後続MISSIONに引き継ぎやすい
- 候補B/Cは、画面の利用頻度が高まり運用上手入力が負担になった場合に、
  改めて承認を得た上で検討する

いずれの候補を選ぶ場合も、**画面実装そのものは本MISSIONの範囲外**であり、
後続MISSIONでの明示的な承認を要する。

## 4. 表示候補（画面に出す情報の案）

`audit_logs` テーブル（`id`, `recorded_at`, `event_type`, `http_method`,
`endpoint`, `status_code`, `permission`, `result_summary`）を元に、以下の
観点で一覧・絞り込み表示することを想定する。

| 表示候補 | 対応する `event_type` / 条件 | 目的 |
|---|---|---|
| 直近の認証失敗 | `event_type = 'auth_denied'`（401） | トークン設定ミス・不正アクセス試行の早期発見 |
| 権限不足 | `event_type = 'permission_denied'`（403） | read/writeトークンでadmin操作が試みられていないかの確認 |
| レート制限超過 | `event_type = 'rate_limited'`（429） | 異常な連続アクセス（誤ったループ処理・想定外の負荷）の検知 |
| admin操作 | `event_type = 'admin_operation'` | 意思決定（`PATCH /api/proposals/<id>`等）や本APIへのアクセスなど、admin権限が使われた操作の一覧 |
| 主要なデータ変更 | `event_type = 'api_call'` かつ `http_method` が `POST`/`PATCH` | employees/missions/tasks等への通常の書き込み操作の一覧 |

いずれも `GET /api/audit-logs` が返す最新順のデータをそのまま利用でき、
画面側で `event_type`/`http_method` によるクライアントサイドの絞り込み
（タブ切り替え等）を行う想定とし、絞り込み用の新規APIパラメータや
サーバー側実装は本MISSIONでは追加しない。

## 5. 画面から監査ログを変更・削除しない方針

- 画面は `GET /api/audit-logs` の表示のみを行い、`audit_logs` に対する
  作成・更新・削除の操作は一切提供しない
- 将来的にも、監査ログの改ざん・削除を可能にする機能（DELETEボタン等）は
  監査ログの証跡としての信頼性を損なうため実装しない方針とする
- 保持期間・件数の整理（`prune_audit_logs`）は既存のサーバー側自動整理
  （30日超過分の削除、最大1000件を超えた古い順の削除）にのみ委ね、
  画面から手動整理を行う機能も追加しない

## 7. 外部公開・外部AI接続には別途承認が必要

- 本設計は**localhost限定運用を前提**とする。`host="127.0.0.1"` 固定・
  `0.0.0.0` バインドなしの現状の運用方針（`docs/MISSION009_auth_design.md`
  2.1・3.6節）をそのまま維持する
- 本画面・本APIをLAN・インターネットへ公開すること、または外部AI
  （GPT・Gemini等）から直接アクセスさせることは、本MISSIONでは一切
  想定・許可しない
- 外部公開・外部AI接続を行う場合は、`docs/MISSION009_auth_design.md`
  3.6節の必須条件（認証・認可機構の完成、HTTPS化、利用者の明示的承認）
  を満たした上で、**別途MISSIONとして利用者の承認を得てから**検討する
